Lessons Learned from Building Software Factories

Henry Duc Bui, Head of Engineering at CloudThinker, shared lessons from applying AI-DLC to the team’s software development process. He showed a monthly chart of merges into the develop branch as an example of how the team tracked its workflow. For me, a metric like this raises follow-up questions about review time, what kinds of changes are merged, and how the team assesses quality. Henry Duc Bui’s session introduction

My talk · New to AWS? Where Should You Start?

In the Education session, I opened with a question about where to start when there are many places to learn AWS. I introduced three resources by the purpose each one serves. This gives students a concrete way to choose their next step, whether that is to learn a concept, complete a workshop, or see how other builders approach a similar problem.

ResourceWhat I introduced
AWS Study GroupStep-by-step workshops, including Vietnamese materials, for practicing how to configure and check AWS resources.
AWS Skill BuilderTopic-based courses, labs, and certification preparation for structured learning.
AWS Builder CenterCommunity articles and workshops, student activities, and badge opportunities subject to the relevant program requirements.

AWS Skill Builder · AWS Builder Center

I used these resources to connect classroom learning with engineering work. A student can learn a concept in a module, verify it with a small lab, and capture the result in a diagram, a screenshot, or a short explanation. When the concept comes up in a project, that record helps explain which service was chosen, how it was tested, and what could be done differently next time.

The talk also mentioned opportunities to explore AWS credits. For a new learner, that is a reason to check the eligibility conditions and get into the habit of tracking costs during the first labs.

AWS Lambda Web Functions and serverless web architecture

The session covered running an application as a native HTTP server on Lambda Web Functions. An application can use a supported Node.js web framework without an adapter specific to Lambda event payloads. A single execution environment can handle multiple requests at the same time. 128 requests is the maximum configurable concurrency per environment. Lambda adjusts the actual limit based on resource usage and load. Lambda Web Functions · Scaling behavior

The session discussed Active CPU Billing and used live benchmarks to compare this model with container-based applications on EC2 and ECS. Web Functions charges include requests, active CPU time, memory over the environment’s lifetime, and data transfer. When interpreting a benchmark, I would compare the shape of the workload, initialization latency, and how much time requests spend waiting for I/O. Execution and billing model

Amazon SQS and asynchronous processing

The Amazon SQS session showed how a queue separates a producer from a worker. The producer can finish accepting the request, while workers process queued messages at a rate the downstream system can handle. The two sides can scale more independently as the amount of work changes.

The diagram at the venue compared Standard and FIFO queues. Standard queues deliver at least once and can deliver out of order. FIFO preserves order within a message group and supports send deduplication. A useful test is to see whether a worker can receive the same job again without repeating a write or changing the job to an incorrect state. SQS Standard · SQS FIFO

My 3-Month AWS Internship Journey

Khang Duong described a three-month internship at FCAJ through the example of building a serverless card game on AWS. The talk connected learning individual services to using them in a project. For students preparing for an internship, it showed one way to explain the experience through implementation steps and lessons from the work.

Starting and sustaining open source contributions

The last session covered finding a first contribution and continuing once the workflow becomes familiar. A small change such as improving a guide or clarifying an issue can teach a newcomer how to read project conventions, communicate with maintainers, and respond to review. My takeaway was to treat each contribution as an example of a problem I investigated and a result I improved.

What I learned as a speaker

  • Start with the audience’s question. For a student new to AWS, asking where to start leads to a concrete action, such as choosing a topic and using a lab to check their understanding.
  • Explain the purpose before introducing the tool. Presenting each learning resource through a specific need makes it easier to remember when to use it.
  • Use examples and evidence when describing what I learned. I can explain a lab or project through its original requirement, what I did, what I observed, and what still needs testing.

Applying the ideas to work

The SQS session relates to the document-processing flow in the Tindy proposal. One test can deliver a PDF scan event more than once and check that the worker updates the document status consistently. I can keep the result with the flow diagram so that the queue’s role is easy to explain when presenting the project.
