Keynote and HCMC Watch Party session

The KEY001 keynote started at 09:00 in the Grand Ballroom in Hanoi. AWS framed it around how builders can tackle ambitious problems with the right tools and resources. The keynote previewed three themes that ran through the program: using AI agents in software development, modernizing workloads, and securing systems as they move into operation. Keynote overview

The catalogue labels the 11:00 session DVT205 as HCMC Watch Party. It shares the topic Building software like never before with agentic AI with DVT203 in Grand Ballroom 3 in Hanoi. The two session codes make it possible to match the watch party listing to its counterpart on the Hanoi agenda. Session catalogue

Topics across the program

  • Agentic AI and software development. The program covered the transition from agent demos to deployment (AIM201), agent-assisted software development (DVT203/DVT205), and patterns for operating multiple agents (AIM301). Sessions PRT301-S and PRT201-S added perspectives on trust and maintaining control as agents become part of business workflows.
  • Data for AI and analytics. Sessions ANT202 and ANT211 focused on building foundations for AI-ready data. ANT201 brought those questions into financial services. ANT205 highlighted work across data silos with Amazon Quick Suite, while ANT214 covered VPBank’s experience scaling a data platform with Amazon Redshift.
  • Application modernization and platform engineering. DEV205 focused on an internal developer platform on EKS. DEV208 described a move from EC2 and PM2 to EKS with GitOps for a NestJS application, while MAM203 addressed the move from a monolith to microservices. AIM303 brought AWS Transform into the modernization of .NET and SQL Server.
  • Operations, security, and cost. DEV401 addressed workload identity, DVT305 focused on application security from design to deployment, and AIM203 addressed defense in depth for agentic workloads. FCAJ contributed DEV204 on S3 storage classes and DEV206 on infrastructure drift remediation. DEV210 added a perspective on controlling Amazon Bedrock spend.

Key takeaways

  • Define how an agent will be evaluated before integrating it. The topics of prototyping, deployment, reliability, and security point to a straightforward design question: what is the agent allowed to do, and how will the team verify the result? For an agent that turns input data into a draft, possible checks include content accuracy, error rates, and cases that require human review.
  • Prepare data for its intended use. An AI or analytics workflow depends on knowing which data is authoritative, who may read it, and how it stays current. These questions matter especially when information is spread across systems or exists in several versions.
  • Choose a modernization approach around the problem at hand. The NestJS, .NET, and internal developer platform examples illustrate different starting points. A team can choose an observable problem such as deployment time, manual effort, or difficulty diagnosing failures and use it to evaluate proposed changes.
  • Consider cost and operations during design. S3 storage classes, monitoring for generative AI, and Bedrock spend are examples of decisions that continue after a system goes live. Storage decisions depend on access frequency. For AI workloads, processing volume, latency, and error rates provide a basis for explaining usage and prioritizing improvements.

Applying the ideas to work

I can use the proposed Tindy architecture to explore three of these topics.

  • Test each stage of PDF processing. For documents processed through S3, GuardDuty, and Amazon Bedrock, useful test cases include valid files, files awaiting a scan, and extraction results with missing fields. The UI can give users a chance to review and confirm a draft before saving it to their profile.
  • Measure costs against actual usage. Two starting measures are the number of PDF extraction requests and the number of new files per month. For S3, object groups with different access frequencies can be evaluated separately before choosing lifecycle rules.
  • Assess the deployment platform against current needs. The program included several Amazon EKS and GitOps examples. For Tindy’s proposed API on Amazon ECS with AWS Fargate, deploying a new version, checking task health, and tracing failures are concrete checks to run before evaluating more complex orchestration requirements.
